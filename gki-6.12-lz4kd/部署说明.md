# 独立工作流方案：LZ4KD 6.12（零侵入 + 可持续 sync 上游）

## 为什么用独立工作流（而不是改原文件）

你的核心诉求是「不影响原逻辑 + 后续能 sync 上游」。我核实过：

- `build.yml` 是纯 `workflow_call` 可复用工作流，**输入里没有任何自定义补丁入口/hook**。
- 要想让 6.12 用新补丁，只有两条路：①改 build.yml（必与上游冲突）；②复制一份自己的（你的思路）。
- 结论：**选②，一个上游文件都不动**。所有新增内容全是新文件，`git merge upstream/dev` 时零冲突。

## 需要放进仓库的文件（共 3 类，全是新增）

```
你的 fork/
├── .github/workflows/
│   ├── build-lz4kd.yml                    ← 新增：复制自 build.yml，仅 zram 步骤改为 6.12 版
│   └── kernel-a16-6-12-lz4kd.yml          ← 新增：入口，use_zram 打开，指向 build-lz4kd.yml
└── lz4kd_612/                             ← 新增：整个目录
    ├── apply_6.12.sh                      ← 注入脚本（zram 步骤调用）
    ├── README.md                          ← 技术说明/风险
    ├── backends/backend_lz4kd.c/.h        ← 6.12 zram backend 适配层
    └── patches/                           ← 8 个补丁
        01~07 + 08 + legacy_6.6_*（共 12 个）
```

**原有文件一个都不改**：`build.yml`、`kernel-a16-6-12.yml`、`zram/`、`config/` 全部保持原样。

## 部署步骤

1. Fork 仓库到你的账号（如果还没 fork）。
2. clone 你的 fork，添加上游 remote：
   ```bash
   git remote add upstream https://github.com/Deemoxzj/GKI_KernelSU_SUSFS.git
   ```
3. 把本交付包的 `deliver/workflows/*.yml` 复制到 `.github/workflows/`；
   把 `deliver/lz4kd_612/` 整个目录复制到仓库根目录。
4. commit + push 到你 fork 的 `dev` 分支。
5. 在 Actions 页会出现新工作流 **「内核构建 - Android 16 (6.12) [LZ4KD 定制]」**，用它触发构建。

## 后续 sync 上游（关键）

因为你的改动全是新文件，上游改的是老文件，两边互不重叠：

```bash
git fetch upstream
git checkout dev
git merge upstream/dev      # 或 git rebase upstream/dev
git push
```

- 你的 2 个新 workflow + `lz4kd_612/` 目录**不会冲突**。
- 上游 `build.yml` 的 bug 修复会正常合入**原 build.yml**，不影响你的 `build-lz4kd.yml`。
- 唯一需要手动维护的：`build-lz4kd.yml` 是你从某个时间点的 build.yml 复制的。上游 build.yml 后续如果有**功能性更新**（比如新的补丁步骤、编译参数改进），你的副本不会自动获得。建议定期对比：
  ```bash
  git diff dev:build.yml dev:build-lz4kd.yml
  ```
  发现上游有新东西值得同步时，手动把这个 diff 里除「zram 步骤」外的改动合并到你的副本。

## 风险速查

- `apply_6.12.sh` 里 SukiSU_patch 路径取自 `github.workspace/SukiSU_patch`（与原 build.yml clone 位置一致），已修正跨 step 变量作用域问题。

- 6.12 上游默认 `use_zram: false` 是原作者知道旧补丁打不上；你的定制工作流显式设为 true。
